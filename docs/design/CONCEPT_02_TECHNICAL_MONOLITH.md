## Purpose

Technical Monolith should present Carlos as someone who builds structured software systems and understands the infrastructure that supports them.

The visual language should feel:

- architectural
- technical
- precise
- structured
- premium
- engineered
- modern
- intentional

It must remain a professional developer portfolio, not a fake operating system or dashboard.

## Core Idea

The page should feel designed through an architectural system or engineering grid. Conceptual references may include:

- technical documentation
- architectural drawings
- engineering schematics
- system diagrams
- industrial product design
- premium technical publications

Do not literally imitate CAD software or blueprints.

## Visual Foundation

- near-black / graphite background
- off-white primary text
- subdued technical gray
- one restrained accent possibility
- visible but subtle structural grid
- sharp spacing logic
- strong alignment
- large typography
- thin technical rules
- indexed sections

Exact colors are intentionally not finalized.

## Typography

This concept should use less editorial serif influence than Concept 01.

- Primary display: strong modern grotesk or geometric sans-serif.
- Technical/meta: monospaced or semi-monospaced type used selectively.
- Optional secondary: restrained serif only if needed for contrast.

The entire site must not become monospace. Final fonts must not be selected or downloaded yet.

## Rejected Patterns

Do not use:

- `✦`
- stars
- sparkles
- Matrix/code rain
- fake terminals
- command-line hero clichés
- green hacker text
- cyberpunk neon overload
- gaming HUD aesthetics
- excessive glassmorphism
- skill percentages
- progress bars
- fake telemetry
- meaningless charts
- fake uptime/data
- fabricated technical values

Technical presentation must always be based on real portfolio content.

## Grid and Structure

The grid is a major visual device. Possible elements include:

- column guides
- thin section boundaries
- oversized numeric indices
- horizontal technical rules
- small metadata blocks
- restrained coordinate-like labels
- modular rectangular regions
- asymmetric but mathematically controlled alignment

The grid must create hierarchy rather than clutter.

## Motion

Motion should feel engineered. Potential behaviors include:

- line drawing
- grid reveals
- masked text entrances
- section number transitions
- image clipping/reveal
- restrained hover state changes

Avoid constant moving grids, excessive parallax, fake scanning effects, blinking terminal cursors, aggressive glitch effects, and animation overload. Support `prefers-reduced-motion`.

## Mobile Philosophy

Mobile should preserve section indices, strong name typography, structured hierarchy, project imagery, and metadata clarity.

It should simplify grid density, dividers, decorative metadata, and motion complexity when necessary. Touch interactions must remain comfortable.

## Accessibility and Performance

Future implementation must prioritize:

- semantic HTML
- keyboard navigation
- visible focus
- contrast
- responsive images
- reduced-motion support
- minimal JavaScript
- performance

Visual grid elements must not interfere with reading order.

## How This Differs from Concept 01

- Concept 01: editorial, atmospheric, serif-led, cinematic restraint.
- Concept 02: architectural, grid-led, system-oriented, with sans/technical typography.

They must not feel like the same layout with different fonts.
